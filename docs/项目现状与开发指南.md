# SeaTunnel Control Plane：项目现状与开发指南

> 记录日期：2026-09-03。本文是开始后续迭代前的交接基线；运行时数据会变化，请以页面和 `npm run status` 为准。

## 1. 当前结论

- 项目是面向 **Apache SeaTunnel Zeta REST API V2** 的单机运维与任务控制台，不是 SeaTunnel 引擎本体。
- 本地开发服务正在运行：Web 为 `http://127.0.0.1:5174/`，Node API 为 `http://127.0.0.1:8800/`。
- 已通过控制台实际连接到 SeaTunnel **2.3.13**：当前为 1 个 Worker、0 个运行中作业、0 个 Pending 作业；页面显示历史完成作业为 316。该数据仅表示本次检查时的集群快照。
- Git 工作区在本次检查开始时处于干净状态（`main`）。

## 2. 技术边界与架构

```text
浏览器
  └─ React 19 + TypeScript + Vite（开发端口从 5174 起自动选择）
       └─ /api 反向代理
            └─ Node.js 原生 HTTP 服务（开发端口从 8800 起自动选择）
                 ├─ 本地 SQLite：用户、会话、任务模板、任务执行记录、Cron、应用设置
                 └─ SeaTunnel REST API V2：集群、作业、日志、监控、提交与停止
```

后端没有 Express/Nest 等框架，也没有 ORM：路由、鉴权、数据库访问均由 `server/*.mjs` 直接实现。SeaTunnel API Base 存于 SQLite 的 `app_settings`，管理员保存设置时会访问 `{base}/overview` 做 5 秒超时的连通性探测。

## 5. 运行、构建和数据位置

```bash
npm run setup       # 安装根目录和 web 依赖
npm run init-db     # 创建 schema；首次启动也会初始化
npm run dev         # 启动 API + Vite
npm run status      # 查看实际端口、PID、日志路径
npm run build       # TypeScript 编译和 Vite 构建
npm run stop        # 停止本地服务
```

- 开发服务会从 API `8800`、Web `5174` 起寻找可用端口；不要把文档或脚本中的端口视为固定值。
- API/Web 日志与 PID 信息位于 `var/`；SQLite 默认位于 `data/seatunnel-control-plane.sqlite`。这两个目录均为运行时数据，不应随意删除。
- 可通过 `EDP_SQLITE_PATH` 改变 SQLite 路径；`EDP_VIZ_PORT` 与 `EDP_WEB_PORT` 可指定服务端口。
- 生产模式由 Node 服务 `web/dist` 静态文件：先执行 `npm run build`，再以 `NODE_ENV=production npm start` 启动。

## 6. 认证与授权现状

- 初始管理员为 `admin` / `123456`（只会在没有该用户时创建）；首次部署后必须改密码。
- 会话使用 SQLite 保存的随机 token，Cookie 为 `HttpOnly; SameSite=Lax`，有效期 7 天。
- 角色只有 `admin` 和 `user`：管理员可管理 SeaTunnel 连接和本地用户；其余业务接口只要求已登录。
- 任务创建、运行、停止作业、提交配置和修改 Tags 尚未按项目/环境/细粒度权限拆分，也没有审计记录。

## 7. 本次实测与已知注意点

1. 登录、首页加载、概览、节点监控、作业与 Pending 摘要在当前本地 SeaTunnel 2.3.13 实例上可用。
2. 当前实例请求 `/resource/workers` 返回 HTTP 404。前端已将该接口作为可选能力处理，并回退使用 `/pending-jobs` 返回的 `clusterSnapshot.workers`，因此首页仍能显示 Worker 信息；但浏览器控制台会留下该 404。后续应确认该接口在目标 SeaTunnel 版本中的支持情况，并考虑在探测后再调用或去除该请求。
3. 未发现自动化测试或 lint 脚本；`package.json` 目前只有启动、构建和数据库初始化脚本。新功能应同时补充至少一层可重复验证（单元、API 或浏览器流程）。
4. 调度器是单个 Node 进程中的 `node-cron`。扩展为多副本前必须引入主节点选举或分布式锁，否则会重复触发任务。
5. 任务路由和 SeaTunnel 代理会将请求体完整读入内存，目前未设请求体大小上限；文件上传/批量提交扩展前应先定义限制和流式策略。
6. 生产部署需补齐 HTTPS、`Secure` Cookie、CSRF 防护、登录限流/密码策略、审计日志与密钥管理。代理当前会复制大部分入站请求头到上游，也应在生产化时改为显式白名单。

## 8. 建议的工作起点

按风险和依赖关系，建议以下顺序推进：

1. **稳定性基线**：补 API/页面回归测试；处理 SeaTunnel REST V2 版本兼容性与可选接口探测。
2. **安全与可追溯性**：默认密码强制修改、最小权限/RBAC、操作审计、请求限制及生产 Cookie 策略。
3. **任务资产能力**：配置校验、版本与回滚、变量/凭据引用、导入导出。
4. **调度可靠性**：并发策略、重试、告警；为多实例部署提供锁或独立调度服务。
5. **平台化能力**：项目/环境/集群模型，然后再建设可视化编排、数据源目录和 GitOps。

## 9. 变更时的约定

- SeaTunnel 的调用集中在 `web/src/api/client.ts`、`server/seatunnel.mjs` 及 `server/index.mjs` 的代理逻辑；新增接口应优先保持这一边界，而非把上游地址散落在页面中。
- 本地控制台元数据与 SeaTunnel 引擎数据是两套数据源：不要假设 SQLite 记录可替代引擎真实状态。
- 任务执行状态仅在列表/详情读取时同步最后一个活跃 Job；若需要完整、实时的执行追踪，应设计独立的轮询/事件同步机制。
- 涉及 SQLite schema 变更时，现有实现仅使用 `CREATE TABLE IF NOT EXISTS`，没有迁移框架；应为增量变更编写可重入迁移，并验证已有数据库升级路径。
